# Catalog 渲染模板风格接入优化方案

## 1. 背景与目标

当前 `dig-ui-skill` 已经积累了大量 catalog 文档与对应 HTML render，例如 `renders/ecommerce/shopify.html`、`renders/dev-tools/superhuman.html`、`renders/creative-tools/figma.html` 等。它们可以快速查看每个 catalog 的 token、字体、按钮、面板与状态样式。

但在实际浏览 render 页面时，能明显感到大部分页面结构、内容样例和组件表达高度相似。不同 catalog 主要只是在同一个预览模板中替换颜色、字体和标题，导致 Shopify、Superhuman、Figma、Raycast、Spotify 等本应差异很大的设计系统，在 render 中呈现出接近同一套 Dig runtime console 的观感。

本方案目标是把 catalog render 从“token 展示页”升级为“catalog 风格样张页”：

- 每个 catalog 不只替换 token，还能体现自身页面类型、组件语义和典型界面场景。
- 保留统一的 Dig render 骨架、语言切换、token 对照和 QA 能力。
- 修复 Raycast、Spotify 等深底深字、不可读的渲染问题。
- 建立自动校验，避免 catalog token 或 HTML render 生成后出现明显 CSS 与可读性错误。
- 让 render 真正服务“选 catalog、审 catalog、回写 catalog”的工作流。

## 2. 当前问题诊断

### 2.1 模板同质化

当前 `sync_renders.py` 的主要策略是：

- 从 catalog markdown 抽取 `name`、`description` 和 `## Dig UI CSS Tokens`。
- 替换 HTML 中的 `:root` token。
- 替换页面标题、描述、语言切换脚本和 token 展示值。
- 复用同一套 `assets/catalog-preview.css` 与同一套 HTML 内容结构。

这会导致所有 catalog 都展示类似内容：

- `Deploy Agents With Control`
- `Agent Execution Overview`
- `Open Console`
- `Execution Trace`
- `Queue: 24`
- `Region: HKG-1`

这些内容适合 Dig runtime 或 developer console，但不适合 Spotify、Shopify、Figma、Superhuman 等品牌化 catalog。最终 render 只能证明 token 被替换了，不能证明该 catalog 适合对应类型的产品界面。

### 2.2 部分 token 语义映射错误

Raycast 与 Spotify 的渲染问题主要来自 token 本身的语义错误，而不是浏览器偶发问题。

例如 Raycast：

```css
--dig-bg: #07080a;
--dig-text: #0d0d0d;
```

Spotify：

```css
--dig-bg: #121212;
--dig-text: #181818;
```

这两组都是深色背景配深色文字，页面会接近不可读。正确映射应从 catalog 的 `on-dark`、`ink`、`body`、`mute` 等文本角色推导，而不是把 surface 色误用为 text 色。

### 2.3 编译器缺少防御性校验

Shopify 的 token block 中存在裸 `css` 行：

```css
css
--dig-bg: #ffffff;
```

当前同步脚本会把这一行原样写入 HTML 的 `:root` 中，形成无效 CSS 内容。类似问题应在编译阶段被过滤或报错。

### 2.4 catalog 文档信息没有被充分利用

许多 catalog markdown 已经包含丰富的品牌描述、组件规则、布局原则和 Do / Don't。但 render 当前只消费 CSS token，较少消费以下信息：

- catalog 所属行业与页面类型。
- 典型组件，例如 command palette、playlist grid、canvas toolbar、checkout card。
- 典型内容密度。
- 黑白 / 彩色 / 图片 / 产品截图的使用方式。
- 品牌特征动作，例如 Spotify 的播放按钮、Raycast 的 command palette、Figma 的多人协作画布。

也就是说，catalog markdown 中已经有“灵魂”，但 render 编译器只拿走了“皮肤”。

## 3. 优化方向

### 3.1 建立 render intent 层

建议在 catalog markdown 中新增可选 `render` 配置，用于声明该 catalog 的预览意图。

示例：

```yaml
render:
  archetype: command-palette-marketing
  page_type: dev-tools
  density: spacious
  canvas: dark-continuous
  hero:
    pattern: product-screenshot
  components:
    - command-palette
    - extension-grid
    - shortcut-keycaps
```

字段建议：

- `archetype`：render 使用的模板类型。
- `page_type`：辅助选择默认内容样例。
- `density`：`compact`、`comfortable`、`spacious`。
- `canvas`：`dark-continuous`、`light-editorial`、`dual-track`、`media-app` 等。
- `hero.pattern`：首屏表达方式，例如 product screenshot、commerce hero、canvas workspace。
- `components`：该 catalog 必须展示的典型组件。

没有 `render` 配置时，继续使用当前 token-sheet 预览作为 fallback，保证兼容。

### 3.2 拆分共享骨架与品牌化 partial

保留统一能力：

- `preview-shell`
- 语言切换
- token 对照表
- swatch 展示
- typography 展示
- responsive 基础布局
- global rules 状态

但将中间的品牌样张区域拆成 archetype partial：

- `command-palette-marketing`：Raycast、Cursor、Warp 等。
- `media-player-shell`：Spotify、Apple Music 类 catalog。
- `creative-canvas-workspace`：Figma、Miro、Webflow、Framer。
- `commerce-dual-track`：Shopify、Airbnb、Nike、Starbucks。
- `inbox-productivity`：Superhuman、Notion、Linear、Cal。
- `ai-console-workbench`：Claude、Mistral、Replicate、Runway。
- `finance-mobile-app`：Wise、Revolut、Coinbase、Kraken。
- `automotive-product-theater`：BMW、Ferrari、Lamborghini、Tesla。

这样 render 的一致性来自 Dig 的编译骨架，差异性来自 catalog 的典型界面场景。

### 3.3 使用 catalog-aware 内容样例

当前默认内容偏 Dig runtime。建议建立内容样例生成器：

```text
dev-tools:
  command, extension, deploy, shortcut, logs

creative-tools:
  canvas, layer, frame, component, collaboration

media-consumer:
  playlist, album, episode, now playing, library

ecommerce:
  merchant, product, checkout, pricing, inventory

saas:
  workspace, team, automation, activity, insight

fintech:
  balance, transfer, card, conversion, verification
```

内容样例不需要追求真实业务完整性，但必须和 catalog 语义一致。这样 Shopify render 不再像 agent console，Spotify render 不再像开发工具，Figma render 不再像 SaaS 控制台。

### 3.4 增加 token 语义校验

新增 catalog render validator，至少检查：

- `--dig-bg` 与 `--dig-text` 对比度。
- `--dig-surface` 与 `--dig-text` 对比度。
- `--dig-surface-strong` 与 `--dig-text-muted` 对比度。
- `--dig-accent` 与 primary button 文字色对比度。
- 必需 token 是否齐全。
- CSS token block 中是否存在非 CSS 变量行，例如裸 `css`。
- HTML 中是否残留默认 Dig runtime 文案。

建议新增命令：

```json
"validate:catalogs": "node validate-dig-catalog-preview.mjs renders"
```

第一阶段可以只做静态检查；第二阶段再接 Playwright 截图和视觉回归。

## 4. 实施步骤

### 阶段一：修复正确性与基础校验

目标是先让现有 render 不再出现明显坏页面。

- 修复 token 抽取逻辑，只接受 `--dig-*` CSS 变量行，过滤裸 `css`。
- 修正 Raycast / Spotify 的 `--dig-text`、`--dig-text-muted`、`--dig-text-soft` 映射。
- 增加 `validate-dig-catalog-preview.mjs`，覆盖 token 缺失、对比度、残留默认文案、裸 CSS 噪音。
- 在 `package.json` 增加 `validate:catalogs`。
- 运行全量 sync 与 validate，记录第一轮问题清单。

验收标准：

- Raycast、Spotify 页面文字可读。
- Shopify render 的 `:root` 不再出现裸 `css`。
- validator 能捕获深底深字、缺失 token 和默认文案残留。

### 阶段二：引入 render intent

目标是让 catalog 可以声明自己的 render 方向。

- 在 `references/catalogs/README.md` 中补充 `render` 协议说明。
- 为 6 个代表 catalog 增加 `render` 配置：
  - Raycast：`command-palette-marketing`
  - Spotify：`media-player-shell`
  - Shopify：`commerce-dual-track`
  - Figma：`creative-canvas-workspace`
  - Superhuman：`inbox-productivity`
  - Wise：`finance-mobile-app`
- 修改 `sync_renders.py`，读取 `render.archetype` 并传入模板选择逻辑。
- 未声明 `render` 的 catalog 继续走现有 fallback。

验收标准：

- 新增 render 配置不会破坏旧 catalog。
- 代表 catalog 可以在 HTML 中带上 `data-render-archetype`。
- index 页面可展示或筛选 archetype。

### 阶段三：拆分品牌化 partial

目标是解决“页面都差不多”的根因。

建议新增目录：

```text
templates/
  catalog/
    base.html
    partials/
      token-sheet.html
      command-palette-marketing.html
      media-player-shell.html
      creative-canvas-workspace.html
      commerce-dual-track.html
      inbox-productivity.html
```

每个 partial 只负责中间样张，不负责全局 shell、语言切换和 token 表。

第一批优先实现：

- `command-palette-marketing`
- `media-player-shell`
- `creative-canvas-workspace`
- `commerce-dual-track`

验收标准：

- Raycast render 能看到 command palette、extension cards、keycaps。
- Spotify render 能看到 sidebar、playlist grid、now playing bar、green play button。
- Shopify render 能看到黑色 cinematic hero 与 cream/mint transaction panel。
- Figma render 能看到 canvas、toolbar、layers panel、collaboration chips。

### 阶段四：可视化回归与持续维护

目标是防止后续 catalog 更新再次把 render 变坏。

- 使用 Playwright 对 catalog render 做 desktop 与 mobile 截图。
- 检查首屏是否空白、主要文字是否可见、关键 section 是否重叠。
- 将截图与日志输出到 `tests/YYYY-MM-DD/catalog-renders/`。
- 在 README 或 update 文档中补充维护流程。

验收标准：

- `npm run validate:catalogs` 可作为日常提交前检查。
- 每次新增 catalog 都能自动检查基础可读性。
- 每次新增 archetype 都有至少一个代表 catalog 作为样例。

## 5. 推荐优先级

建议按以下顺序推进：

1. 修复 CSS token 抽取与 Raycast / Spotify / Shopify 已知问题。
2. 增加 catalog validator，防止坏 token 继续进入 render。
3. 为代表 catalog 加 `render` intent。
4. 实现 3-4 个 archetype partial。
5. 全量迁移高价值 catalog。
6. 引入 Playwright 可视化回归。

这样可以先保证 render 正确，再逐步提升 render 的表达力，不需要一次性重写所有 catalog 页面。

## 6. 设计原则

- Catalog render 不是品牌官网复刻，而是 catalog 能力样张。
- 统一来自 Dig 的 shell、token、QA 和交互规则；差异来自 catalog 的典型组件与场景。
- 不要为了差异化引入一次性装饰，所有变化都应来自 catalog token、render intent 和可复用 partial。
- 不要让 preview 过度营销化。它仍然要服务设计系统审查、catalog 维护和页面实现参考。
- 如果 catalog 文档已经写明关键组件，render 应优先展示这些组件，而不是使用通用 Dig runtime 示例。

## 7. 预期效果

完成后，浏览 `renders/` 应该能获得三层信息：

- 这个 catalog 的颜色、字体和 token 是否正确。
- 这个 catalog 适合什么类型的产品页面。
- 这个 catalog 在典型 UI 场景中是否真正成立。

这会让 `dig-ui-skill` 的 catalog 从静态风格文档变成可验证、可比较、可持续维护的设计系统资产。
